# 前后端代码开发规范

> 所有环境唯一业务数据库为 PostgreSQL；Redis 只承载可恢复协调状态。历史持久化实现的退出规则见 [ADR-0001](./decisions/0001-postgresql-only.md)。

## 1. 通用规范

- 所有新增或修改的代码、SQL、schema 和迁移脚本必须使用详细中文注释，说明用途、字段/参数语义、约束原因、数据归属、生命周期和异常边界，便于后续 RAG 检索。
- 注释必须与实现同步更新，不得写空泛注释，不得在注释中记录 API Key、Client ID 原值、客户隐私或其他敏感数据。

- 业务命名遵循根目录 `CONTEXT.md`，中文文档与英文代码术语保持一一对应。
- 小步提交，每个提交只解决一个完整问题；推荐 Conventional Commits。
- 禁止提交 `.env`、数据库文件、密钥、访问令牌、真实客户数据和构建缓存。
- 新行为必须有相应测试；缺陷修复必须先有可复现的回归测试。
- 不允许为了通过检查而关闭类型、Lint 或安全规则。

建议提交类型：

```text
feat: 新功能
fix: 缺陷修复
docs: 文档
test: 测试
refactor: 不改变行为的重构
chore: 工具或依赖维护
```

分支建议：`feature/<主题>`、`fix/<主题>`、`docs/<主题>`。`main` 始终保持可运行。

## 2. Python 后端规范

### 2.1 版本与风格

- Python 3.12+，使用完整类型标注。
- Ruff 负责格式和静态规则，mypy 使用严格模式。
- 行长度不超过 100；导入按标准库、第三方、项目代码分组。
- 所有 `backend/app` 下除 `__init__.py` 外的 Python 文件都必须有模块级中文 docstring，说明模块职责、边界和主要协作对象。
- 所有类都必须有中文类 docstring，说明类的职责、状态边界、生命周期和对外协作关系；协议类还要说明实现方必须遵守的契约。
- 所有方法和函数（包括 `__init__`、私有辅助方法、异步方法和路由处理函数）都必须有中文 docstring。不能用“执行某某流程并返回结果”这类空泛描述代替业务语义。
- 方法 docstring 必须按实际签名完整说明：
  - `Args`：逐一解释每个参数的业务含义、单位、允许范围、是否可为空、数据来源和安全约束；`self`/`cls` 不写。
  - `Returns`：说明返回对象的业务含义、字段语义、顺序、空值含义和是否为快照/推导结果；无返回值也要写明“无返回值”。
  - `Raises`：列出调用方可观察或必须处理的异常类型，并说明触发条件；不会向调用方传播的内部异常不要伪造列出。
- 数据类字段、Pydantic 字段、协议方法和适配器转换函数必须说明字段语义、单位、来源、生命周期和不可违反的业务规则。金额、重量、尺寸和费率尤其不能只依赖变量名表达含义。
- 对外接口的方法必须优先使用可复制的完整模板：

  ```python
  def calculate(value: int, rate_bps: int) -> int:
      """按版本化费率计算单件费用。

      Args:
          value: 以最小货币单位表示的计费基数，必须大于等于零。
          rate_bps: 以基点表示的费率，`100` 表示 1%，范围为 0～10000。

      Returns:
          按最小货币单位四舍五入后的费用；不会返回浮点金额。

      Raises:
          ValueError: 计费基数或费率超出业务允许范围时抛出。
      """
  ```

- 异常说明必须和实现一致：输入校验错误使用领域异常或 `ValueError`，外部 Ozon/数据库/网络错误必须在边界层转换为稳定的项目异常；禁止用宽泛的 `Exception` 掩盖业务失败。
- 复杂公式、舍入方式、版本匹配、降级策略和安全决策必须在代码旁补充中文注释；docstring 说明“做什么”，行内注释说明“为什么这样做”。
- 禁止裸 `except:`、可变默认参数和无边界重试。

### 2.2 分层依赖

```text
API → 应用 → 领域
          ↘ 基础设施适配器
```

- `api`：HTTP 协议、参数校验、依赖注入、响应转换。
- `application`：用例、权限、事务和操作编排。
- `domain`：业务模型、规则和端口，不依赖 FastAPI、PostgreSQL 驱动、Redis 或 Ozon 传输模型。
- `infrastructure`：PostgreSQL、Redis、Ozon HTTP、加密、文件和日志适配器。
- API 路由不得直接执行 SQL；领域层不得导入基础设施模块。

### 2.3 FastAPI

- 路由必须声明请求与响应模型。
- 查询参数给出范围限制，外部输入不可直接拼接 SQL 或 URL。
- 依赖通过 `Depends` 注入，便于 Stub 和测试替换。
- 错误转换集中处理，不把 Ozon 原始错误或凭据返回前端。
- 长任务通过同步任务模型执行，不阻塞 HTTP 请求。

### 2.4 PostgreSQL 与 Redis

- 使用参数化语句，禁止字符串拼接 SQL。
- 每个操作明确连接和事务边界。
- PostgreSQL 外键必须显式定义；写操作尽量短，避免长期持有事务和行锁。
- 金额不使用浮点数；标识符不强制转换为整数。
- 表结构变化同步修改 `database/postgresql_schema.sql`、数据库文档和测试；SQL 变更必须补充中文注释。

### 2.5 Ozon 集成

- 扩展代码中禁止出现 `Client-Id`、`Api-Key`。
- 请求统一处理超时、请求编号、分页、限流、重试和脱敏日志。
- Ozon 传输模型与领域模型分离，并进行运行时校验。
- 读取默认可按错误分类重试；重要写入必须预览、确认、幂等和审计。
- 不猜测上游路径、字段、枚举、配额或弃用时间。

### 2.6 可替换外部服务

- 模型、邮件、导入文件和备份存储必须通过 `ModelGateway`、`MailGateway`、`ImportObjectStore` 和 `BackupObjectStore` 等端口隔离，领域层不导入厂商 SDK。
- 供应商、地址、模型/发件身份、超时和配额由后端配置选择；业务代码不得写死厂商名称或密钥。
- 开发和自动化测试使用 Mail Sink、Fake 或本地适配器，不调用真实模型、邮件或对象存储服务。
- 外部调用失败必须分类为可重试、不可重试或需要人工处理；重试有上限，不得回滚已经提交且独立成立的业务事实。

## 3. React/TypeScript 前端规范

### 3.1 类型与组件

- 开启 TypeScript 严格模式，禁止无说明的 `any`。
- 组件使用函数组件；组件名称 PascalCase，函数和变量 camelCase。
- 每个组件聚焦一个职责，复杂状态提取为自定义 Hook。
- API 类型集中维护，不在多个组件复制响应结构。
- 服务端数据与纯 UI 状态分离。

### 3.2 状态与请求

- 每个请求必须处理加载、成功、空数据、失败和重试。
- 请求可取消，组件卸载后不得更新状态。
- 分页游标视为不透明字符串。
- 不在 `useEffect` 中制造重复请求；稳定依赖并处理 React 严格模式。
- 错误信息面向运营人员，调试细节只进入脱敏日志。

### 3.3 界面与可访问性

- 使用语义化 HTML，表单控件必须有可访问名称。
- 键盘可操作，焦点状态清晰；不只依赖颜色表达状态。
- 正文和交互元素满足可读对比度。
- 侧边栏适配窄宽度，不产生无必要横向滚动。
- 保持中文术语与需求文档一致。

### 3.4 Chrome 扩展

- 使用 Manifest V3 和最小权限。
- 页面、内容脚本、Service Worker 之间的消息必须校验类型和来源。
- 后端操作采用固定白名单，不接受任意 URL 或请求体透传。
- 不把密钥、客户隐私或敏感响应保存到 `chrome.storage`。
- 提交前检查生产包中的清单、Source Map 和权限。

## 4. 测试规范

| 层级 | 测试内容 | 依赖 |
|---|---|---|
| 单元测试 | 领域规则、映射、错误分类 | 无网络、无数据库 |
| 集成测试 | PostgreSQL 持久化、约束、RLS、事务与迁移 | 每次测试隔离的 PostgreSQL database/schema |
| 契约测试 | Ozon 成功、认证失败、限流、超时、畸形响应 | Mock |
| API 测试 | 路由、权限、校验、分页和错误格式 | FastAPI TestClient |
| 前端测试 | 组件状态和用户交互 | Stub API |
| E2E | 加载扩展、切换工作区、浏览和刷新 | Playwright + Stub |

测试名称描述用户可观察行为，不测试私有方法。不得在自动测试中调用真实 Ozon 账户。

## 5. 合并检查

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\check.ps1
```

该命令必须完成：

- pytest
- Ruff
- mypy
- TypeScript 类型检查
- Vite 生产构建

## 6. 代码评审清单

- 功能是否符合需求和统一领域语言。
- 是否泄露凭据、客户数据或敏感日志。
- 是否存在跨工作区访问风险。
- 是否正确处理分页、空数据、限流和失败。
- 是否引入不必要权限、依赖或复杂度。
- 文档、SQL、接口定义和测试是否同步。
- 是否能在 PostgreSQL 与 Redis 就绪、无真实 Ozon 凭据条件下运行 Stub 模式。
