# 通用软件项目全生命周期 Agent Skills 指南

本文提供一套不绑定具体行业、代码仓库、技术栈或 AI 平台的软件项目全生命周期 skills 编排方法。它适用于 Web、移动端、桌面端、浏览器扩展、SaaS、企业应用、数据平台以及包含 AI Agent 的产品。

这里的“skill”不仅指某个市场上的同名安装包，也指一个能够被 Agent 稳定执行、具有明确输入、步骤、产出和质量门禁的工程能力单元。

## 一、为什么采用“双层 Skills 模型”

市场上的具体 skill 会持续变化：名称会变、维护者会变、安装量会变，也可能被新的工具替代。因此，不建议直接把项目流程绑定到一组固定包名。

推荐将 skills 分成两层：

```text
第一层：稳定的工程能力槽位
需求分析、架构设计、API 设计、测试策略、安全审计、部署、可观测性……

第二层：可替换的具体实现
某个 skills.sh 包、组织内部 skill、Codex skill、MCP 工具、CLI、云平台连接器……
```

选择具体 skill 时，优先检查：

1. 来源是否可信，例如成熟开源项目、官方厂商或专业组织。
2. 工作流是否明确，能否说明输入、步骤、输出和停止条件。
3. 是否要求读取真实项目证据，而不是只输出通用建议。
4. 是否具备测试、回滚、审计和证据产出能力。
5. 是否存在危险权限、外部写操作或敏感数据外传风险。
6. 是否持续维护，是否有用户量、社区反馈和安全审计。
7. 是否与当前技术栈和团队规范兼容。

## 二、生命周期总图

```text
市场与机会研究
  ↓
产品规划与立项
  ↓
需求发现、分析与规格化
  ↓
领域建模与体验设计
  ↓
系统架构、数据、API 与安全设计
  ↓
原型、前端、后端与基础设施开发
  ↓
代码评审与持续集成
  ↓
单元、集成、契约、E2E、验收、性能、安全、兼容性测试
  ↓
发布准备、部署、浏览器/设备验证
  ↓
监控、事件响应与持续优化
  ↓
项目总结、知识沉淀与下一周期规划
```

## 三、推荐的核心 Skill 组合

### 1. `project-orchestrator`：项目执行编排

**介绍：** 贯穿生命周期的主控 skill，负责读取项目上下文、拆解目标、维护计划、协调专项 skills、验证结果和生成交接记录。

**适用时机：** 从立项到交付的所有中大型任务。

**使用方法：**

- 开始时读取仓库规则、状态、产品文档、架构和测试。
- 将目标转换为可观察结果和验收标准。
- 根据任务风险调用专项 skills。
- 控制范围，保留用户已有改动。
- 结束时检查变更、验证证据、未完成项和剩余风险。

**输入：** 项目目标、代码仓库、现有文档、时间和质量约束。

**输出：** 计划、执行记录、改动、验证结果、风险和 handoff。

### 2. `market-research`：市场与竞品研究

**介绍：** 分析目标市场、用户群、竞争产品、替代方案、定价、渠道和趋势。

**适用时机：** 产品立项、方向调整、功能优先级和商业验证。

**使用方法：**

- 明确市场边界、地域、客户类型和时间范围。
- 使用一手资料、公开数据、用户评论和竞品实际产品验证。
- 区分事实、推断和假设。
- 输出竞品矩阵、机会空间和需要验证的关键假设。

**输入：** 产品想法、目标用户、地域、预算和商业目标。

**输出：** 市场地图、竞品矩阵、机会假设、风险和研究来源。

### 3. `product-planning`：产品规划

**介绍：** 将市场机会转化为产品愿景、范围、路线图、里程碑和成功指标。

**适用时机：** 项目启动、版本规划和路线图调整。

**使用方法：**

- 定义目标用户和需要解决的问题。
- 写清目标、非目标、约束和依赖。
- 使用 RICE、WSJF、MoSCoW 或 Cost of Delay 等方法排序。
- 为里程碑定义可量化的退出标准。

**输出：** Product Brief、路线图、里程碑、指标树和风险清单。

### 4. `requirements-analysis`：需求分析

**介绍：** 把访谈、业务文档和想法转换为完整、无歧义、可测试的需求。

**适用时机：** PRD 编写、需求评审、变更分析和验收准备。

**使用方法：**

- 提取角色、目标、触发条件、主流程和异常流程。
- 为每项需求补充权限、数据、审计、性能和合规条件。
- 将“系统应当好用”等模糊描述转为可验证标准。
- 建立需求到设计、代码和测试的追踪关系。

**输出：** 用户故事、用例、业务规则、验收标准和需求追踪矩阵。

### 5. `spec-review`：规格评审

**介绍：** 对照真实代码、架构和运行环境检查规格中的错误假设、遗漏和不可实施内容。

**适用时机：** 需求进入设计或开发之前。

**使用方法：**

- 核对规格中提到的数据、接口、模块和现有行为。
- 检查成功、失败、权限、并发、回滚和迁移场景。
- 标记事实错误、待决策项和实现风险。
- 未通过评审的规格不进入开发。

**市场示例：** skills.sh 上的 `spec-review` 类 skill 展示了“规格与代码库事实核验”的工作方式，但选择时仍应检查来源质量和维护情况。

### 6. `domain-modeling`：领域建模

**介绍：** 建立统一语言、实体、值对象、状态、业务不变量和上下文边界。

**适用时机：** 业务术语混乱、跨团队协作、复杂状态和核心业务设计。

**使用方法：**

- 找出同词不同义和一物多名。
- 使用具体场景挑战模型。
- 明确实体身份、生命周期、所有权和不变量。
- 只把稳定领域语言写入领域词汇表；技术取舍写 ADR。

**输出：** 领域词汇、上下文图、状态模型、业务规则和领域事件。

### 7. `ux-research`：用户体验研究

**介绍：** 通过访谈、可用性测试、行为数据和任务分析理解用户真实需求。

**适用时机：** 需求发现、原型验证、体验问题调查和版本复盘。

**使用方法：**

- 定义研究问题和样本标准。
- 设计中立的访谈或测试脚本。
- 区分用户陈述、实际行为和研究者推断。
- 输出洞察、证据、严重度和设计建议。

**输出：** 研究计划、访谈记录、任务地图、洞察和机会列表。

### 8. `product-design` / `frontend-design`：产品与前端设计

**介绍：** 将需求和用户任务转换为信息架构、用户流程、线框图、视觉系统和交互状态。

**适用时机：** 新产品、前端原型、设计系统和界面重构。

**使用方法：**

- 先确定用户任务和信息层级，再处理视觉风格。
- 同时设计加载、成功、空数据、错误、权限拒绝和恢复状态。
- 建立字体、色彩、间距、组件和动效 token。
- 对关键流程制作可交互原型并进行用户测试。

**输出：** 信息架构、用户流程、线框图、原型、视觉规范和组件清单。

### 9. `accessibility-review`：无障碍设计与审计

**介绍：** 检查语义结构、键盘操作、焦点、对比度、屏幕阅读器和认知可访问性。

**适用时机：** 设计评审、前端开发、验收和发布门禁。

**使用方法：**

- 以 WCAG 目标级别定义验收标准。
- 进行自动扫描、键盘操作和屏幕阅读器检查。
- 确认状态不只用颜色表达。
- 将关键无障碍行为纳入自动化测试。

**输出：** 无障碍问题清单、严重度、复现步骤和修复验证。

### 10. `system-architecture`：系统架构设计

**介绍：** 定义系统边界、服务、模块、通信、部署拓扑、质量属性和演进策略。

**适用时机：** 新系统、重大能力、系统拆分、扩容或技术迁移。

**使用方法：**

- 从业务能力和质量属性开始，而不是先选框架。
- 记录关键数据流、同步/异步边界和故障传播方式。
- 对可用性、性能、安全、成本和复杂度做权衡。
- 用 ADR 记录难以逆转且存在真实取舍的决策。

**输出：** 上下文图、容器图、组件图、部署图、质量属性场景和 ADR。

### 11. `api-design`：API 与事件契约设计

**介绍：** 设计 HTTP、GraphQL、RPC 或事件接口的资源、字段、错误、版本和兼容策略。

**适用时机：** 服务协作、前后端协作、第三方开放平台和事件驱动系统。

**使用方法：**

- 先定义消费者场景和契约，再实现服务。
- 明确认证、授权、幂等、分页、限流、错误和重试语义。
- 使用 OpenAPI、AsyncAPI、GraphQL Schema 或 protobuf 固化契约。
- 通过契约测试防止消费者和提供者漂移。

**输出：** 接口规范、错误模型、版本策略和契约测试。

### 12. `database-schema-design`：数据模型与迁移设计

**介绍：** 设计数据所有权、结构、约束、索引、生命周期和迁移安全。

**适用时机：** 新功能、数据平台、报表、数据迁移和性能优化。

**使用方法：**

- 区分业务事实、派生数据、缓存和审计数据。
- 定义主键、唯一约束、外键、状态边界和保留周期。
- 基于真实查询模式设计索引。
- 使用 expand-migrate-contract 等渐进方式完成高风险迁移。

**输出：** 逻辑模型、物理 schema、迁移、回滚和数据质量规则。

### 13. `threat-modeling`：威胁建模

**介绍：** 在开发前识别资产、参与者、信任边界、攻击面和缓解措施。

**适用时机：** 认证、支付、敏感数据、文件、外部调用、AI Agent 和高权限功能。

**使用方法：**

- 绘制数据流和信任边界。
- 使用 STRIDE、PASTA 或攻击树分析风险。
- 将缓解措施转为设计约束和安全测试。
- 为剩余风险指定负责人和接受条件。

**输出：** 威胁模型、攻击面、风险等级和安全需求。

### 14. `secure-coding`：安全默认开发

**介绍：** 针对语言和框架应用输入验证、授权、秘密管理、依赖安全和安全日志实践。

**适用时机：** 所有涉及用户输入、认证、数据、文件、网络和外部工具的开发。

**使用方法：**

- 加载与当前语言和框架匹配的安全指南。
- 将安全规则融入实现和测试，而不是上线前集中补救。
- 对危险操作、跨租户访问和敏感数据增加明确控制。

**输出：** 安全实现、安全测试和偏离规范的决策记录。

### 15. `tdd`：测试驱动开发

**介绍：** 使用“失败测试—最小实现—持续切片”的方式开发稳定行为。

**适用时机：** 核心业务规则、缺陷修复、接口和复杂状态逻辑。

**使用方法：**

1. 确定公共接口和测试 seam。
2. 写一个能够失败的行为测试。
3. 编写最小实现使其通过。
4. 重复下一个垂直切片。
5. 在评审阶段进行结构重构。

**输出：** 可执行规格、单元测试、集成测试和回归保护。

### 16. `language-framework-best-practices`：语言与框架工程实践

**介绍：** 针对 Python、Java、Go、Rust、React、Vue、Angular、iOS、Android 等技术栈提供类型、安全、性能和可维护性指导。

**适用时机：** 实现、重构和代码评审。

**使用方法：**

- 只加载当前技术栈相关的指南。
- 服从项目自身规范和架构约束。
- 不通过关闭 lint、类型或安全规则来让检查通过。

**输出：** 符合栈规范的实现、静态检查结果和评审建议。

### 17. `code-review`：代码评审

**介绍：** 对变更范围进行正确性、可维护性、性能、安全和测试完整性审查。

**适用时机：** PR、合并前、重大重构和发布前。

**使用方法：**

- 先读取需求、diff、相关代码和测试。
- 只报告真实且可操作的问题。
- 优先关注缺陷、数据损坏、安全问题和行为回归。
- 评论定位到变更行，并给出触发场景和影响。

**市场示例：** Flutter 官方仓库公开了完整的 `code-review` 工作流；通用 `review` 类 skill 也常用于检查意图与执行是否发生漂移。

### 18. `qa-testing-strategy`：风险驱动测试策略

**介绍：** 根据系统架构、缺陷来源和业务风险决定测试层次、覆盖方式和发布门禁。

**适用时机：** 项目测试规划、测试套件失衡、E2E 过多或发布质量不稳定时。

**使用方法：**

- 识别关键用户旅程和高风险模块。
- 在单元、组件、契约、集成、E2E、属性和模糊测试之间选择最小有效层。
- 定义合并门禁、部署门禁、flake SLO 和测试预算。
- 为失败保留日志、trace、截图和负责人。

**市场示例：** skills.sh 的 `qa-testing-strategy` 强调风险驱动、测试形状、发布证据和 flaky test 治理。

### 19. `contract-testing`：契约测试

**介绍：** 验证服务提供者、消费者、消息和第三方依赖的接口兼容性。

**适用时机：** 微服务、前后端分离、事件驱动和外部 API 集成。

**使用方法：**

- 固化请求、响应、错误和事件 schema。
- 在 CI 中验证消费者和提供者。
- 对第三方 API 使用沙箱、Stub 或录制后脱敏的夹具。

**输出：** 契约、兼容性报告和集成回归测试。

### 20. `browser-e2e`：真实浏览器端到端测试

**介绍：** 使用 Playwright、WebDriver 或浏览器控制工具执行真实用户流程。

**适用时机：** Web、管理后台、电商、浏览器扩展和跨页面流程。

**使用方法：**

```text
打开页面 → 获取稳定页面状态 → 操作 → 页面变化后重新定位
→ 断言结果 → 保存截图、trace、视频或网络日志
```

- 覆盖关键路径，不把所有细节都堆到 E2E。
- 测试正常、空数据、失败、重试、权限和会话失效。
- 对 flaky 测试记录根因，不使用无限重试掩盖问题。

**输出：** E2E 测试、截图、trace、视频和验收证据。

### 21. `acceptance-testing`：业务验收测试

**介绍：** 从用户和业务目标验证产品是否达到可交付标准。

**适用时机：** 迭代结束、UAT、候选版本和正式发布前。

**使用方法：**

- 将需求验收标准转换为可执行案例。
- 明确环境、数据、角色、步骤和预期结果。
- 对失败案例记录证据、严重度和责任归属。

**输出：** UAT 报告、通过/失败状态、缺陷和签收记录。

### 22. `performance-testing`：性能与容量测试

**介绍：** 验证响应时间、吞吐、并发、资源、容量和稳定性。

**适用时机：** 高流量、实时系统、大数据、发布前容量评估和性能回归。

**使用方法：**

- 先定义 SLO 和真实流量模型。
- 执行基准、负载、压力、峰值、浸泡和容量测试。
- 同时采集应用、数据库、缓存、队列和基础设施指标。
- 报告 P50/P95/P99、吞吐、错误率和资源瓶颈。

**输出：** 性能基线、容量结论、瓶颈、调优结果和剩余风险。

### 23. `security-audit`：安全审计

**介绍：** 从真实攻击面出发查找可利用漏洞，而不是只做样式化清单检查。

**适用时机：** 高风险功能、发布前、重大变更、外部审计和安全事件后。

**使用方法：**

- 明确资产、攻击者、信任边界和变更范围。
- 检查认证、授权、注入、SSRF、文件、秘密、日志、依赖和供应链。
- 为每个发现提供位置、触发方式、影响、严重度和修复建议。
- 修复后执行回归和再验证。

**市场示例：** Cloudflare 的 `security-audit` skill 强调寻找具有真实影响的可利用漏洞；OWASP 的 Agent 安全 skill 适合检查工具权限、提示注入和数据外传路径。

### 24. `compatibility-testing`：兼容性测试

**介绍：** 验证不同浏览器、设备、操作系统、分辨率、网络和辅助技术下的行为。

**适用时机：** Web、移动端、桌面端、扩展和全球化产品。

**使用方法：**

- 根据用户数据定义支持矩阵。
- 覆盖主流版本、最小视口、缩放、触摸、键盘、深色模式和慢网。
- 使用自动化做广度检查，真实设备做高风险抽样。

**输出：** 支持矩阵、问题列表、降级策略和兼容结论。

### 25. `mobile-device-testing`：移动端与真机测试

**介绍：** 验证 iOS/Android 真机上的安装、权限、后台、网络、性能和系统集成。

**适用时机：** 原生 App、Flutter、React Native、PWA 和移动 Web。

**使用方法：**

- 覆盖低端机、主流机型和关键系统版本。
- 验证冷启动、后台恢复、权限拒绝、弱网、升级和崩溃恢复。
- 采集崩溃、ANR、内存、电量和网络证据。

**输出：** 真机矩阵、性能报告、崩溃记录和发布建议。

### 26. `ci-cd`：持续集成与持续交付

**介绍：** 建立从代码提交到构建、测试、制品、部署和回滚的自动化管线。

**适用时机：** 项目初始化、发布提速、质量门禁和环境标准化。

**使用方法：**

- 将 lint、类型、测试、构建、安全扫描和制品签名加入流水线。
- 使用不可变制品在环境间晋级。
- 分离合并门禁、部署门禁和发布门禁。
- 配置最小权限、秘密管理和审计日志。

**输出：** CI/CD 配置、制品、质量门禁、部署记录和回滚流程。

### 27. `infrastructure-as-code`：基础设施即代码

**介绍：** 使用 Terraform、Pulumi、CloudFormation 或平台模板管理基础设施。

**适用时机：** 云资源、网络、数据库、集群、权限和多环境管理。

**使用方法：**

- 模块化管理环境差异。
- 先 plan，再 apply；高风险变更需要审批。
- 扫描权限、公开端口、加密和状态文件风险。
- 为灾难恢复和环境重建定期演练。

**输出：** IaC 模块、变更计划、环境清单和恢复验证。

### 28. `container-kubernetes`：容器与编排

**介绍：** 设计镜像、容器运行时、Kubernetes 工作负载、弹性和发布策略。

**适用时机：** 容器化、微服务、弹性扩缩容和多环境部署。

**使用方法：**

- 构建最小、可复现、非 root 镜像。
- 配置资源限制、健康检查、Pod 安全和网络策略。
- 使用滚动、蓝绿或金丝雀发布。

**输出：** 镜像、部署清单、策略、容量设置和发布验证。

### 29. `release-management`：发布管理

**介绍：** 管理版本、变更、迁移、审批、发布窗口、回滚和沟通。

**适用时机：** 候选版本、生产发布和重大迁移。

**使用方法：**

- 汇总功能、缺陷、迁移、风险和支持准备情况。
- 定义 go/no-go 条件和回滚触发器。
- 使用 feature flag、分批发布和观察窗口降低风险。
- 发布后核对业务指标和技术 SLO。

**输出：** 发布清单、变更日志、审批记录、回滚方案和发布结论。

### 30. `observability`：监控与可观测性

**介绍：** 使用指标、日志、trace、事件和业务信号理解生产系统行为。

**适用时机：** 上线前、生产运行、性能排查和可靠性建设。

**使用方法：**

- 为关键用户旅程定义 SLI/SLO。
- 使用结构化日志、关联 ID 和分布式追踪。
- 告警基于用户影响和可行动性，避免告警噪声。
- 仪表板同时展示业务与技术指标。

**输出：** SLO、告警、仪表板、日志规范和追踪方案。

### 31. `incident-response`：故障响应

**介绍：** 对生产事故进行分级、止损、沟通、恢复和复盘。

**适用时机：** 服务中断、数据错误、安全事件和重大性能退化。

**使用方法：**

- 指定事件负责人和沟通渠道。
- 优先止损和恢复，再调查根因。
- 保存时间线、证据和决策。
- 复盘聚焦系统改进，不做个人归责。

**输出：** 事件时间线、状态通知、恢复记录、根因和行动项。

### 32. `documentation`：工程文档

**介绍：** 创建和维护需求、架构、API、运维、用户和交付文档。

**适用时机：** 所有阶段。

**使用方法：**

- 将知识放入唯一且合适的位置。
- 代码行为用测试固化，重大决策用 ADR，故障恢复用 runbook。
- 文档变更与实现一起评审。
- DOCX、PDF、PPT 等正式制品生成后进行渲染检查。

**输出：** PRD、架构文档、API 文档、ADR、runbook、用户手册和交付报告。

### 33. `knowledge-management`：知识沉淀与检索

**介绍：** 将项目知识组织为可维护、可检索、适合人和 Agent 使用的知识库。

**适用时机：** 长周期项目、多团队协作、RAG、交接和复盘。

**使用方法：**

- 区分永久规范、决策、故障知识、测试事实和临时进度。
- 为大文档使用语义分块、元数据和版本信息。
- 定期检查过期、重复和冲突内容。

**输出：** 文档地图、术语表、知识库、检索策略和维护责任。

### 34. `project-retrospective`：项目复盘

**介绍：** 对目标、交付、质量、协作、成本和流程进行结构化总结。

**适用时机：** 里程碑结束、重大发布、事故后和项目结束。

**使用方法：**

- 对照最初目标和指标评估结果。
- 分析哪些做法有效、哪些失效以及原因。
- 行动项必须有负责人、期限和验证方式。
- 将稳定经验更新到规范、skill、模板、测试或自动化。

**输出：** 项目总结、经验教训、行动项和下一周期计划。

### 35. `skill-creator`：组织内部 Skill 建设

**介绍：** 将重复出现、需要专业判断的工作流沉淀成组织自己的 skill。

**适用时机：** 同类任务重复三次以上、跨团队执行不一致或通用市场 skill 不适配内部规则时。

**使用方法：**

- 明确 skill 的触发条件、边界和非目标。
- 写清输入、步骤、工具、安全限制、产出和验证。
- 配套模板、脚本、参考资料和测试用例。
- 版本化维护并记录变更。

**输出：** 可复用的内部 skill、模板、脚本和使用说明。

## 四、各阶段的 Skills 编排

### 阶段 1：市场研究与项目规划

推荐顺序：

```text
market-research
  → product-planning
  → requirements-analysis
  → project-orchestrator
```

阶段门禁：

- 目标用户和问题有证据支持。
- 成功指标可量化。
- 项目目标、非目标和依赖明确。
- 关键市场假设有后续验证计划。

### 阶段 2：需求分析与规格化

推荐顺序：

```text
ux-research
  → requirements-analysis
  → domain-modeling
  → spec-review
```

阶段门禁：

- 每项需求有角色、触发、主流程、异常和验收标准。
- 权限、数据、审计、性能和合规要求已考虑。
- 规格与真实代码和环境不存在明显冲突。

### 阶段 3：体验与架构设计

推荐并行编排：

```text
产品体验：product-design → accessibility-review → prototype-validation

技术设计：system-architecture
          → api-design
          → database-schema-design
          → threat-modeling
```

阶段门禁：

- 关键用户旅程完成原型验证。
- 模块、数据和信任边界清晰。
- API、schema、错误、迁移和安全策略可实施。
- 重大技术取舍已记录 ADR。

### 阶段 4：开发

推荐顺序：

```text
tdd
  → language-framework-best-practices
  → secure-coding
  → code-review
```

前端追加：`frontend-design`、`accessibility-review`、`browser-e2e`。

后端追加：`api-design`、`database-schema-design`、`contract-testing`。

平台工程追加：`infrastructure-as-code`、`container-kubernetes`、`ci-cd`。

阶段门禁：

- 新行为有测试。
- lint、类型、单元和相关集成测试通过。
- 安全关键路径有拒绝和恶意输入测试。
- diff 经过独立代码评审。

### 阶段 5：质量验证

推荐顺序：

```text
qa-testing-strategy
  ├─ unit / component testing
  ├─ contract testing
  ├─ integration testing
  ├─ browser-e2e
  ├─ acceptance-testing
  ├─ performance-testing
  ├─ security-audit
  ├─ accessibility-review
  └─ compatibility / mobile-device testing
```

阶段门禁：

- 关键旅程有自动化或可审计的人工证据。
- 性能达到已定义 SLO。
- 严重安全问题关闭或正式接受风险。
- 支持矩阵中的关键环境通过验证。
- flaky、跳过和阻塞测试均有记录。

### 阶段 6：发布与交付

推荐顺序：

```text
ci-cd
  → release-management
  → infrastructure-as-code
  → browser / device verification
  → observability
```

阶段门禁：

- 使用已验证、不可变和可追踪的制品。
- 数据迁移和回滚已经演练或验证。
- 监控、告警、runbook 和支持人员就绪。
- go/no-go 标准明确。

### 阶段 7：运行、总结与持续改进

推荐顺序：

```text
observability
  → incident-response（发生事故时）
  → project-retrospective
  → documentation
  → knowledge-management
  → skill-creator
```

阶段门禁：

- 结果与最初目标、SLO 和商业指标完成对照。
- 重大经验进入 ADR、测试、runbook 或内部 skill。
- 行动项有负责人、期限和验证方式。

## 五、完整测试体系

| 测试类型 | 解决的问题 | 主要证据 |
|---|---|---|
| 静态检查 | 类型、语法、规范和已知模式错误 | lint、typecheck、扫描报告 |
| 单元测试 | 独立业务规则是否正确 | 测试报告、覆盖率 |
| 组件测试 | UI 或模块在受控环境中是否正确 | DOM/组件断言、截图 |
| 属性测试 | 大量输入下不变量是否成立 | 随机种子、失败样本 |
| 模糊测试 | 非预期输入是否导致崩溃或漏洞 | corpus、crash case |
| 契约测试 | 服务、事件和客户端是否兼容 | schema、provider/consumer 报告 |
| 集成测试 | 数据库、队列、缓存和服务协作是否正确 | 日志、测试结果、容器状态 |
| E2E 测试 | 真实用户流程是否可完成 | trace、截图、视频 |
| 验收测试 | 产品是否满足业务要求 | UAT 报告、签收记录 |
| 性能测试 | 速度、容量和稳定性是否达标 | P50/P95/P99、吞吐、资源图 |
| 安全测试 | 是否存在可利用风险 | 漏洞报告、复现证据、再验证 |
| 无障碍测试 | 辅助技术用户能否完成任务 | 扫描、键盘和读屏记录 |
| 兼容性测试 | 支持矩阵中行为是否一致 | 浏览器/设备矩阵、截图 |
| 混沌与恢复测试 | 依赖故障后系统能否降级和恢复 | 故障注入、恢复时间、数据校验 |
| 生产冒烟测试 | 发布后关键能力是否正常 | 健康检查、业务探针和指标 |

## 六、市场 Skills 的选择建议

不建议只看安装量。安装量高说明接受度，但不能替代安全和适配性审查。推荐按以下顺序选择：

1. 官方厂商、成熟开源项目、标准组织或可信团队维护。
2. 有清晰工作流、输入输出和边界。
3. 有公开仓库、版本历史和问题反馈。
4. 有安全扫描或可读源码。
5. 能产出可验证证据，而不只是建议文本。
6. 能与现有代码规范、审批和权限系统集成。

本次市场取样中值得参考的方向包括：

- [skills.sh](https://skills.sh/)：开放 Agent Skills 市场和排行榜。
- [Flutter code-review skill](https://www.skills.sh/flutter/flutter/code-review)：来自成熟项目的结构化代码评审工作流。
- [Cloudflare security-audit skill](https://www.skills.sh/cloudflare/security-audit-skill/security-audit)：强调真实可利用影响的安全审计。
- [OWASP agent-security-audit skill](https://www.skills.sh/owasp/secure-agent-playbook/agent-security-audit)：覆盖 Agent 权限、提示注入、工具调用和数据外传。
- [QA testing strategy skill](https://www.skills.sh/vasilyu1983/ai-agents-public/qa-testing-strategy)：覆盖风险驱动测试、测试门禁和 flaky test 治理。
- [Agentforce test skill](https://www.skills.sh/forcedotcom/sf-skills/agentforce-test)：展示了 AI Agent 产品的功能、安全和 trace 测试闭环。

这些链接是能力设计参考，不代表应当未经审查直接安装。安装前仍需检查最新版本、权限、源码、维护状态和组织合规要求。

## 七、推荐的最小组织级 Skill 套件

如果一个团队从零建设 Agent Skills 工程体系，建议先落地以下 16 个核心能力：

1. `project-orchestrator`
2. `market-research`
3. `product-planning`
4. `requirements-analysis`
5. `spec-review`
6. `domain-modeling`
7. `system-architecture`
8. `api-design`
9. `database-schema-design`
10. `frontend-design`
11. `tdd`
12. `code-review`
13. `qa-testing-strategy`
14. `security-audit`
15. `ci-cd-release`
16. `observability-incident-response`

第二批再补充性能、兼容性、无障碍、移动真机、IaC、Kubernetes、知识管理和内部 skill 创建能力。

## 八、Skill 本身的标准模板

每个内部 skill 至少应包含：

```text
名称与目的
触发条件
不适用场景
所需输入
必须读取的上下文
执行步骤
允许使用的工具
安全与权限限制
产出格式
质量门禁
停止或阻塞条件
示例
版本与维护者
```

一个 skill 只有在“不同执行者能得到接近的结果，而且结果可以被验证”时，才真正具备工程价值。

## 九、生命周期交付总门禁

- [ ] 市场和用户问题有证据支撑。
- [ ] 目标、非目标、指标和验收标准明确。
- [ ] 领域语言、架构、API、数据和 UI 设计一致。
- [ ] 新行为有自动化测试或可审计验证。
- [ ] 代码通过 lint、类型、测试、构建和评审。
- [ ] 性能达到 SLO，容量风险有记录。
- [ ] 安全、隐私、合规和供应链风险已检查。
- [ ] 无障碍和兼容性符合支持矩阵。
- [ ] 数据迁移、部署和回滚可执行。
- [ ] 浏览器或设备关键流程已完成真实验证。
- [ ] 监控、告警、runbook 和事件响应准备就绪。
- [ ] 发布结果与业务指标和技术指标完成核对。
- [ ] 经验已进入文档、ADR、测试、自动化或内部 skill。

## 十、结论

成熟的生命周期 skills 体系不是“安装越多越好”，而是形成以下闭环：

```text
证据驱动规划
  → 可测试规格
  → 可演进设计
  → 测试驱动实现
  → 风险驱动验证
  → 可回滚交付
  → 可观测运行
  → 经验沉淀为下一轮能力
```

具体 skill 可以替换，但这套闭环及其质量门禁应保持稳定。
