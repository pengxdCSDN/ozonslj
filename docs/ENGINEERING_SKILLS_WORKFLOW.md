# 项目周期工程 Skills 运用流程

本文为 `ozonslj` 项目整理一套从规划到交付复盘的工程 skills 使用方法。目标是让每个阶段都有明确的输入、执行方式、产出物和质量门禁，避免只调用技能而没有形成可验证结果。

## 一、使用原则

1. `project-run` 贯穿整个项目周期，负责重建上下文、规划、实施、验证和交接。
2. 先读取 `AGENTS.md`、`CONTEXT.md` 以及相关 `docs/`，再修改代码或文档。
3. 需求、领域模型、API、数据库、前端类型、测试和交付文档必须保持一致。
4. 新行为必须有测试；缺陷优先先写回归测试。
5. Ozon 相关自动化测试只能使用 Stub、Mock 或契约夹具，不访问真实账户。
6. 每个阶段都要形成可观察结果：文档、代码、测试、截图、报告或交付清单。

## 二、全流程总览

```text
项目规划
  ↓
需求分析与领域建模
  ↓
架构、API、数据库与交互设计
  ↓
文档与验收标准
  ↓
前后端开发与前端原型实现
  ↓
单元 / 集成 / 验收 / 性能 / 安全 / 兼容性测试
  ↓
浏览器验证与交付
  ↓
项目总结、ADR、故障沉淀与交接
```

## 三、Skills 目录

### 1. `project-run`

**定位：** 本仓库的主流程 skill，负责从仓库证据出发完成规划、开发、验证、文档和 handoff。

**适用时机：** 所有项目开发、恢复工作、调试、交付和阶段性总结任务。

**用法：**

- 开始前执行 `git status --short`，保留用户已有修改。
- 按任务读取 `CONTEXT.md`、需求、架构、API、数据库和开发文档。
- 检查实际代码和测试，不仅依赖文档推断行为。
- 将请求转为可观察结果，先做最小完整改动。
- 先执行聚焦检查，再根据风险运行完整检查。
- 收尾时检查 scoped diff、`git diff --check`，并报告已验证、未验证和剩余风险。

**主要产出：** 项目计划、实施结果、验证记录、交付说明和 handoff。

### 2. `domain-modeling`

**定位：** 建立和维护领域模型、统一语言和上下文边界。

**适用时机：** 需求存在术语歧义、实体关系不清、业务规则需要确认或架构决策依赖领域定义时。

**用法：**

- 对照 `CONTEXT.md` 检查用户使用的术语。
- 对模糊词提出精确的领域表达。
- 用具体场景验证实体关系和边界条件。
- 发现术语后及时更新 `CONTEXT.md`。
- 只有在决策难以逆转、具有真实取舍且未来不易理解时才创建 ADR。

**主要产出：** 领域词汇、上下文边界、业务规则、领域场景和 ADR。

### 3. `grill-with-docs`

**定位：** 用现有文档、领域模型和架构决策反向质询项目计划。

**适用时机：** 需要评审需求、挑战方案、发现计划漏洞或确认设计是否符合既有约束时。

**用法：**

- 把计划逐条对照 `CONTEXT.md`、需求、架构和 ADR。
- 追问遗漏的边界场景、失败路径、数据所有权和验收条件。
- 将已经确定的决策同步回对应文档。

**主要产出：** 计划修订、风险列表、决策记录和待澄清问题。

### 4. `database-schema-design`

**定位：** 设计实体所有权、约束、索引、迁移和查询模型。

**适用时机：** 新增实体、修改表结构、设计工作区隔离、处理状态数据或需要迁移安全性时。

**用法：**

- 先明确业务事实与派生数据。
- 定义主键、外键、唯一约束、删除策略和数据边界。
- 为高频查询设计索引，说明索引原因。
- 设计迁移顺序、回滚策略和兼容旧版本的过渡期。
- 同步 `database/postgresql_schema.sql`、`docs/DATABASE.md` 和测试。

**主要产出：** schema、迁移脚本、约束说明、索引方案和数据模型文档。

### 5. `supabase-postgres-best-practices`

**定位：** 提供 PostgreSQL 查询、索引、事务和性能优化建议。

**适用时机：** 编写或审查 SQL、处理大数据量、排查慢查询或优化数据库配置时。

**用法：**

- 检查查询条件和排序是否有合适索引。
- 评估分页方式、连接数量、事务边界和锁竞争。
- 用实际查询计划验证优化结果，而不是只凭经验添加索引。

**主要产出：** 查询改进、索引调整、性能基线和数据库风险说明。

### 6. `api-design`

**定位：** 设计 HTTP API 的资源、请求、响应、错误、分页和兼容策略。

**适用时机：** 新增或修改 FastAPI 接口、前后端协作或需要稳定契约时。

**用法：**

- 先定义用户可观察行为，再设计接口。
- 明确请求校验、响应结构、错误码、空数据和重试语义。
- 统一分页、排序、过滤和幂等规则。
- 同步 `docs/API.md`、后端模型、前端类型和契约测试。

**主要产出：** API 契约、错误模型、版本兼容策略和契约测试。

### 7. `ozon-seller-api`

**定位：** 处理 Ozon Seller API 的客户端、认证、分页、限流、重试、Stub 和 UI 接入。

**适用时机：** 任何商品、价格、库存、订单、物流、财务、报告或 Ozon API-backed UI 工作。

**用法：**

- 实现前核对官方资料或现有项目契约，不猜测路径、字段和枚举。
- 将 Ozon 传输模型与领域模型隔离。
- 为超时、限流、分页、部分失败和重复请求定义策略。
- 测试使用 Stub、Mock 和契约夹具，禁止访问真实账户。

**主要产出：** Ozon 适配器、请求模型、响应转换、Stub、契约测试和故障处理说明。

### 8. `python-best-practices`

**定位：** 提升 Python 后端的类型安全、异常处理、接口设计和可维护性。

**适用时机：** 编写、重构或审查 Python、FastAPI、服务接口、数据模型和业务逻辑时。

**用法：**

- 使用完整类型标注，保持 mypy strict 可通过。
- 明确异常类型、边界和调用方处理方式。
- 为公共类和复杂逻辑写简短中文 docstring 或注释。
- 不使用裸 `except`、无边界重试和隐藏异常。

**主要产出：** 可维护的 Python 模块、类型检查结果和代码评审意见。

### 9. `frontend-design`

**定位：** 设计具有明确视觉方向、布局、字体、色彩和交互层次的前端界面。

**适用时机：** 新页面、前端原型、界面重塑、品牌页和复杂交互设计时。

**用法：**

- 先确定页面类型、用户、视觉语言和信息密度。
- 先画页面结构，再实现组件。
- 同时设计加载、空数据、错误、成功和重试状态。
- 以响应式、可访问性和操作效率约束视觉方案。

**主要产出：** 页面原型、组件结构、视觉规范和交互状态定义。

### 10. `design-taste-frontend`

**定位：** 避免模板化、千篇一律的前端视觉，适合落地页、作品集和视觉重设计。

**适用时机：** 产品介绍页、品牌页、营销页或需要明确视觉风格的重设计任务。

**用法：**

- 先输出一句 Design Read，说明页面类型、用户和审美方向。
- 根据场景设置视觉变化、动效强度和信息密度。
- 优先使用已有设计系统或官方组件库，不混用多个设计系统。
- 检查移动端、减少动画、对比度和降级方案。

**注意：** 这是视觉设计 skill，不应单独替代后台数据界面的可用性和无障碍规范。

### 11. `vercel-react-best-practices`

**定位：** 优化 React / Next.js 的组件、数据获取、渲染和 bundle 性能。

**适用时机：** React 组件开发、重渲染排查、页面性能优化和前端代码审查时。

**用法：**

- 减少不必要的状态和组件重渲染。
- 正确划分客户端交互组件和静态组件。
- 评估数据请求、缓存、懒加载和 bundle 体积。
- 对大列表、复杂表格和连续输入重点检查渲染成本。

**主要产出：** React 性能改进、组件边界建议和前端性能检查结果。

### 12. `web-design-guidelines`

**定位：** 审查网页的可访问性、交互一致性、响应式和界面质量。

**适用时机：** UI 评审、UX 检查、浏览器验收和上线前界面审计时。

**用法：**

- 检查语义化 HTML、键盘焦点、ARIA、对比度和错误提示。
- 检查窄屏布局、横向滚动、触控目标和减少动画。
- 确认状态不只通过颜色表达。

**主要产出：** UI 审计清单、问题等级和修复建议。

### 13. `tdd`

**定位：** 以红—绿—重构循环驱动可验证的功能开发。

**适用时机：** 新功能、缺陷修复、回归测试和集成测试任务。

**用法：**

1. 先确定要测试的公共接口和 seam。
2. 编写一个描述行为的失败测试。
3. 实现使测试通过的最小代码。
4. 重复下一个垂直切片。
5. 在独立评审阶段再做重构。

**主要产出：** 单元测试、集成测试、回归测试和清晰的行为规格。

### 14. `security-best-practices`

**定位：** 对 Python、JavaScript/TypeScript 和 Web 应用进行安全设计与安全审查。

**适用时机：** 用户明确要求安全评审、安全加固或需要安全默认实现时。

**用法：**

- 同时识别后端和前端技术栈。
- 检查认证、授权、工作区隔离、SQL 注入、XSS、CSRF、SSRF、CORS、CSP、日志脱敏和依赖风险。
- 检查扩展权限、浏览器存储和凭据边界。
- 高风险问题按严重度、影响和修复优先级输出报告。

**主要产出：** 安全设计建议、安全审计报告、风险等级和修复计划。

### 15. `playwright`

**定位：** 使用真实浏览器进行导航、交互、截图、数据提取和 UI 流程验证。

**适用时机：** 浏览器验收、端到端流程、响应式检查、回归验证和 UI 调试时。

**用法：**

```text
打开页面 → snapshot → 使用稳定元素引用操作
→ 页面变化后重新 snapshot → 截图 / trace → 记录结果
```

- 操作前必须获取 snapshot。
- 导航、弹窗、菜单或页面重大变化后重新获取 snapshot。
- 验证产物放入 `output/playwright/`。
- 先确认 Node/npm 和 `npx` 可用。

**主要产出：** 验收记录、截图、trace、流程问题和浏览器验证结论。

### 16. `browser:control-in-app-browser`

**定位：** 控制 Codex 内置浏览器，适合访问、点击、输入、查看页面状态和本地 Web 验证。

**适用时机：** 需要复用当前应用浏览器状态、检查可见页面或进行交互式本地验证时。

**用法：**

- 打开目标页面并检查当前可见状态。
- 按用户流程点击、输入和切换页面。
- 对关键页面保存截图或记录实际结果。

**主要产出：** 页面状态、验证截图、交互问题和验收结论。

### 17. `chrome:control-chrome`

**定位：** 控制用户已有的 Chrome 状态，包括标签页、登录会话和已安装扩展。

**适用时机：** 需要使用真实 Chrome 会话、已登录账户或已安装扩展验证时。

**用法：**

- 先识别目标标签页和当前登录状态。
- 验证扩展加载、侧边栏、权限和页面交互。
- 不将真实凭据、客户数据或敏感截图写入项目。

**主要产出：** Chrome 环境验证结果、扩展行为记录和兼容性问题。

### 18. `chrome-extensions`

**定位：** 开发和发布 Manifest V3 Chrome 扩展。

**适用时机：** 修改 manifest、service worker、side panel、content script、消息通信或扩展权限时。

**用法：**

- 检查 Manifest V3 结构和最小权限。
- 验证 service worker 生命周期和消息传递。
- 检查 `chrome.storage` 中只保存允许的数据。
- 构建后确认 manifest 引用的文件真实存在。
- 通过 Chrome 实际加载扩展并验证关键流程。

**主要产出：** 扩展源码、构建产物、权限说明和 Chrome 验收记录。

### 19. `documents` / `minimax-docx`

**定位：** 生成、编辑和验证 Word 文档。

**适用时机：** 用户明确需要 `.docx`、正式报告、合同、方案或可打印文档时。

**用法：**

- 读取并遵守对应 skill 的模板和格式要求。
- 生成后渲染为图片或 PDF 做视觉检查。
- 发现分页、表格、字体或页眉页脚问题后迭代。

**主要产出：** 经过渲染验证的 DOCX 和必要的 PDF 预览。

### 20. `pdf`

**定位：** 读取、生成、提取和检查 PDF，尤其关注视觉布局。

**适用时机：** 需求 PDF、报告 PDF、表单、交付文档或 PDF 视觉验收时。

**用法：**

- 先提取文本和元数据。
- 对关键页面渲染截图检查布局。
- 处理表格、分页、字体、图片和表单字段。

**主要产出：** PDF 文件、提取结果、渲染截图和布局问题清单。

### 21. `pptx-generator` / `presentations`

**定位：** 生成、读取和编辑 PowerPoint 或演示文稿。

**适用时机：** 项目汇报、架构评审、阶段总结和交付演示时。

**用法：**

- 从受众和汇报目标确定页面结构。
- 将项目结果、指标、风险和下一步组织为演示逻辑。
- 生成后检查文字溢出、图表、分页和视觉一致性。

**主要产出：** 汇报 PPT、架构演示和项目总结材料。

### 22. `excalidraw-diagram-generator`

**定位：** 生成架构图、流程图、关系图和思维导图。

**适用时机：** 需要可视化系统边界、数据流、用户流程或模块关系时。

**用法：**

- 先确定图的目的和读者。
- 明确节点、边、方向和分层。
- 生成 `.excalidraw` 文件后检查信息是否完整、关系是否有歧义。

**主要产出：** 可在 Excalidraw 打开的架构图或流程图。

### 23. `chunking-strategy`

**定位：** 为 RAG、向量库和大文档处理设计分块策略。

**适用时机：** 需求文档、API 文档、PDF 或知识库需要检索增强时。

**用法：**

- 按语义边界切分，而不是机械按字符截断。
- 结合文档结构选择 256—1024 token 的块大小。
- 通常使用 10%—20% 重叠。
- 用检索精度、召回率和语义完整性评估结果。

**主要产出：** 分块规则、元数据设计和检索评估结果。

### 24. `ocr-document-processor` / `paddleocr-doc-parsing`

**定位：** 从扫描件、图片和复杂 PDF 中提取文字、表格、公式和版面结构。

**适用时机：** 需求来源是扫描 PDF、发票、财报、复杂表格或多栏文档时。

**用法：**

- 先识别文档类型和页面布局。
- 提取文本、表格、公式和图表结构。
- 对关键表格和阅读顺序进行人工抽查。
- 将解析结果交给需求分析和领域建模流程。

**主要产出：** Markdown、JSON、表格数据和版面解析结果。

## 四、按项目阶段编排 Skills

### 阶段 A：项目规划

使用：`project-run` → `domain-modeling` → `grill-with-docs` → `database-schema-design` / `api-design`。

产出：范围、里程碑、风险、领域词汇、初始架构和验收目标。

门禁：目标可观察、非目标明确、已有文档约束已检查。

### 阶段 B：需求文档分析

使用：`project-run` → `domain-modeling` → `grill-with-docs`；复杂文档追加 `ocr-document-processor` / `paddleocr-doc-parsing` / `chunking-strategy`。

产出：用户故事、用例、异常流程、领域规则和验收标准。

门禁：每项需求至少有成功、空数据和失败场景。

### 阶段 C：架构设计

使用：`domain-modeling` → `database-schema-design` → `api-design` → `ozon-seller-api` → `security-best-practices`。

产出：模块边界、API 契约、数据库模型、外部集成方案、权限和安全边界。

门禁：领域层、API 层、基础设施层职责清晰；迁移、错误和兼容策略明确。

### 阶段 D：文档产出

使用：`project-run`、`grill-with-docs`，根据格式选择 `documents` / `minimax-docx`、`pdf`、`presentations`、`excalidraw-diagram-generator`。

产出：需求、架构、API、数据库、ADR、流程图、报告和汇报材料。

门禁：渲染检查通过；文档与代码、schema、测试一致。

### 阶段 E：开发与前端原型

后端使用：`python-best-practices` → `ozon-seller-api` → `tdd`。

前端原型使用：`frontend-design` → `design-taste-frontend` → `web-design-guidelines`。

前端实现使用：`vercel-react-best-practices` → `chrome-extensions` → `tdd`。

产出：领域逻辑、API、数据库变更、前端页面、扩展功能和对应测试。

门禁：加载、成功、空数据、错误、取消和重试状态完整；类型检查和测试通过。

### 阶段 F：测试

使用：`tdd`、`project-run`、`ozon-seller-api`、`security-best-practices`、`playwright`、`web-design-guidelines`。

测试层次：

1. 单元测试：领域规则、转换、校验和纯组件。
2. 集成测试：API、应用服务、数据库和 Redis。
3. 契约测试：Ozon Stub、API 响应和前端类型。
4. 验收测试：用户完整流程。
5. 性能测试：API P95、慢查询、首屏、列表渲染和大数据量。
6. 安全测试：认证、授权、隔离、注入、XSS、SSRF、CSP、凭据和日志。
7. 兼容性测试：Chrome、Edge、窄屏、宽屏、慢网、断网、键盘和减少动画。

门禁：所有失败、跳过和环境阻塞项都有明确记录。

### 阶段 G：验证交付

使用：`project-run` → `playwright` → `browser:control-in-app-browser` / `chrome:control-chrome` → `chrome-extensions` → `web-design-guidelines`。

验证顺序：

```text
git 状态与 diff
  → pytest / Ruff / mypy
  → schema 验证
  → TypeScript / Vite 构建
  → 扩展加载
  → 浏览器关键流程
  → 截图 / trace
  → 安全与兼容性检查
  → git diff --check
```

产出：构建产物、验证记录、截图、trace、已知问题、部署说明和回滚说明。

### 阶段 H：项目总结

使用：`project-run` → `grill-with-docs` → `domain-modeling`；正式总结可追加 `documents` / `presentations`。

产出：完成情况、指标、风险、技术复盘、ADR、故障文档、测试补充和 handoff。
