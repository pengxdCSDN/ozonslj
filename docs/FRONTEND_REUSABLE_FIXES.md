# 前后端界面问题与可复用修复流程

> 本文沉淀模型供应商、RAG 配置等页面迭代中反复出现的问题，作为后续前后端开发、联调和验收的复用基线。文档不记录任何 API Key、密码或真实业务凭据。

## 1. 页面问题分类

### 1.1 布局与视觉一致性

- 页面必须使用统一内容容器：固定最大宽度、左右内边距和卡片间距，避免卡片边缘互相覆盖。
- 表单采用明确网格：三列字段在宽屏下对齐，Model/Base URL 等长字段独占一行；窄屏降为单列，不产生横向滚动。
- 卡片标题、状态徽标、空状态和操作区使用统一垂直节奏；按钮放在同一操作栏，主按钮、次按钮、危险按钮保持一致高度和圆角。
- 原生 `select` 的下拉菜单容易受浏览器主题和层叠上下文影响。需要可控样式时使用可访问的自定义组合框，必须支持键盘导航、Escape 关闭和点击外部关闭。
- 不在生产界面显示开发占位词（如 `NEW`、`Stub`、示例供应商名称）；空状态应说明原因、下一步和可执行入口。
- 长列表或多段卡片必须保证页面滚动容器高度可用；不能通过固定高度裁切底部内容。需要折叠时提供明确的展开状态。

### 1.2 交互与状态管理

- 页面状态至少区分：初始加载、加载中、成功、有数据、空数据、失败、保存中、测试中和已取消。
- “刷新”必须调用列表查询接口；请求成功后以服务端结果为准更新页面，不能只做本地重绘。
- “新增、编辑、保存、删除、停用、测试连接、生成降级链”等按钮必须绑定真实后端接口；禁止只改变展示状态。
- 新增或编辑成功后自动触发同一列表查询流程，确保排序、优先级和服务端生成字段立即可见。
- 操作按钮在请求期间应禁用并显示进度；请求结束后恢复，避免重复提交和鼠标持续旋转。
- 编辑已有凭据时，后端应按资源 ID 读取已保存的凭据；前端空白 API Key 表示“沿用原值”，不得把掩码值回传覆盖真实值。
- 失败提示要包含用户可行动作；开发者诊断信息写入受控日志，不直接暴露凭据或内部堆栈。

### 1.3 后端操作结果 Toast

- 所有后端请求都必须反馈结果：成功使用 `message_success`，失败使用 `message_error`，普通状态使用信息提示。
- 结果优先使用右上角 Toast 弹窗，不用长期停留的普通内联文字代替操作反馈；Toast 默认展示 3 秒后自动隐藏，新结果出现时重新计时。
- 失败 Toast 使用 `role="alert"`，成功和普通 Toast 使用 `role="status"`，同时提供 `aria-live="polite"`；不能只依赖颜色区分状态。
- 请求期间按钮必须禁用并显示进行中状态；请求完成后恢复，成功和失败都要恢复按钮可用状态。
- 错误消息必须说明可行动原因：字段为空、字段格式/类型错误、HTTP 状态码、认证失败、网络失败或服务端凭据缺失；禁止只显示“请求失败”。
- 成功消息必须说明实际完成的动作；涉及外部模型时还应说明请求是否发出、目标主机和响应状态，但不得显示 API Key、令牌或完整上游响应。
- 每个页面的反馈状态应集中管理，避免同一请求同时出现互相矛盾的 Toast、内联提示和旧状态。
- 首次进入页面的初始化查询和操作完成后的静默数据同步不得显示“成功”Toast；只有用户主动点击刷新或提交操作时才提示成功。初始化失败仍必须显示可行动的错误提示。

### 1.3 API 契约与后端联动

- 前端 API 类型、后端 Pydantic 请求模型、响应模型和测试夹具必须同步修改。
- 创建接口使用显式字段：`model_type`、`provider_name`、`protocol`、`model`、`base_url`、`api_key`、`priority`；后端校验必填项、URL 格式、优先级范围和租户归属。
- 测试连接接口支持新建和已保存资源两种模式：新建必须提供 API Key；已保存资源允许省略 API Key，由后端安全读取凭据存储。
- 列表接口返回脱敏后的凭据标记（如是否已配置、掩码摘要），绝不返回原始 API Key。
- 所有写接口必须具备幂等或重复提交保护；数据库写入和凭据写入的事务边界要明确。
- 供应商降级按用途独立维护（Embedding、翻译/意图/重写/答案），按数值优先级排序；限额、超时、网络错误和明确的供应商不可用状态才触发下一级。

## 2. 推荐实现流程

1. 先读取 `CONTEXT.md`、相关需求/架构/API 文档和现有路由、组件、测试。
2. 用浏览器复现：记录 URL、操作步骤、请求方法、状态码、响应摘要和控制台错误；不截图或复制敏感凭据。
3. 先补最小回归测试：校验请求模型、资源归属、空 API Key 复用、错误映射和列表刷新行为。
4. 修改领域/API 契约，再修改前端类型和交互；避免在组件内拼接 SQL 或直接依赖数据库实现。
5. 使用统一的异步请求封装处理取消、超时、重试和错误提示；按钮状态由请求状态驱动。
6. 验证桌面宽屏、窄屏、浏览器原生主题以及滚动到底部；重点检查下拉层、固定容器和底部操作区。
7. 运行相关 pytest、Ruff、mypy、TypeScript、Vite 构建和 `git diff --check`；记录失败项及环境阻塞。
8. 提交前核对 `git status --short`，只提交任务范围内文件；部署后用真实页面重新验证新增、刷新、编辑、测试和降级链。

## 3. 验收清单

- [ ] 页面无重叠、裁切、横向滚动和不可见底部内容。
- [ ] 所有按钮都有明确后端请求、加载态、成功态和失败态，并通过统一 Toast 呈现结果。
- [ ] 成功/失败 Toast 分别使用 `message_success` / `message_error`，3 秒自动隐藏且具备正确无障碍角色。
- [ ] 新增成功后列表自动刷新，刷新按钮单独可重复执行。
- [ ] 编辑后测试连接不会错误要求再次输入已保存 API Key。
- [ ] API Key 只在输入时使用，列表、日志、错误和截图均为脱敏信息。
- [ ] 下拉选项真实来自固定枚举或后端配置，空列表有可理解提示。
- [ ] 供应商按用途分池，优先级可配置，失败可自动降级并留下可审计原因。
- [ ] 前后端契约、数据库约束、测试和文档同步。
