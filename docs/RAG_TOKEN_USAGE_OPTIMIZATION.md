# RAG 评测 Embedding 消耗优化记录

## 结论

已将正式 RAG 评测索引改为“按评测套件懒加载 + 按切片 ID 断点续传”。30 例、120
例、240 例不再在首次启动时一次性生成整套向量；运行哪个套件，只为该套件需要的冻结
案例调用 Embedding。后续扩大评测范围时，只补写 Chroma 中缺少的 `gold-*` 切片。

这次优化不改变问题、人工标注、切片内容、Embedding 模型、向量维度、检索指标或质量
门槛，只改变索引准备时机和重复调用策略，因此不会用“少测数据”伪造质量通过。

## 优化前后

当前 `fixed-rag-v2` 共有 400 个案例：160 个校准案例、240 个冻结验收案例。拒答和未
收录案例不生成证据切片，多意图案例生成 10 个证据切片，普通支持案例生成 5 个切片。
按当前固定语料计算，Embedding 输入字符量如下（实际 token 以供应商 tokenizer 和返回
usage 为准）：

| 场景 | 优化前首次准备 | 优化后首次准备 | 预计减少的切片/输入量 |
| --- | ---: | ---: | ---: |
| 30 例 quick | 1,800 / 191,900 字符 | 140 / 14,805 字符 | 92.2% |
| 120 例 standard | 1,800 / 191,900 字符 | 540 / 57,570 字符 | 70.0% |
| 240 例 full | 1,800 / 191,900 字符 | 1,080 / 115,140 字符 | 40.0% |

优化前的 1,800 个切片包含校准集，但 30/120/240 正式质量门禁只使用冻结集；校准集
仍保留在代码和离线契约中，不会被删除，也不会影响离线评测。上述比例是索引准备阶段
的输入量比例，不是整次质量评测的总成本；正式评测仍会产生 Reranker、文本模型和查询
Embedding 调用。

## 运行逻辑

1. Worker 根据 `run.suite` 调用 `evaluation_engine(quick|standard|full)`。
2. 领域层生成对应冻结案例的稳定 `gold-*` 切片；`None` 仍可用于离线完整语料校验。
3. Worker 用 Chroma `/get` 按 ID查询已有切片，只对缺失 ID 按每批 64 条调用真实 Embedding。
4. 每批成功后立即写入 Chroma；中途失败时，重试只补缺失切片，不重复已成功的调用。
5. 同一 Worker 先执行 quick、再执行 standard/full 时，每次都会重新检查 ID 缺口，避免
   运行时布尔缓存导致后续套件漏建索引。

## 对生产的影响

- 正面：首次 30 例不再提前消耗完整评测索引额度，预算阻断概率和等待时间显著降低；
  重试不会反复扣除已成功写入切片的 Embedding 额度。
- 不变：Chroma collection 仍为独立的 `ozonslj_rag_evaluation`，不污染业务知识库；
  证据 ID、引用校验、Recall/Precision、拒答和主备降级门槛不变。
- 代价：第一次从 quick 扩大到 standard/full 时会产生新增切片的 Embedding 调用；这是
  必要成本，不应通过删除 collection 或反复重建来绕过。
- 边界：如果供应商当天预算已经达到硬上限，优化不会伪造可用额度；应等待周期重置或
  由管理员调整 Embedding 日限额后再补建缺失切片。

## 验收与回滚

验收顺序固定为：确认 Embedding 主/备用绑定和维度 → 创建 quick → 确认 30/30、错误 0
且质量通过 → 再创建 standard → 最后创建 full。回滚时只需回退代码版本；已有 Chroma
切片仍可按稳定 ID复用。不得删除 collection 作为常规修复手段，除非确认模型维度或
语料版本发生不兼容变化，并已安排完整重建额度。

## 可复用约束

以后所有需要真实 Embedding 的批量任务都应优先采用：按业务批次懒加载、稳定 ID 幂等、
先查询缺口、分批写入、失败后补缺口。禁止仅用 collection count 判断是否完成，禁止在
重试时无条件重新 Embedding 全量文本，禁止把预算错误解释为供应商 Key 无效。
